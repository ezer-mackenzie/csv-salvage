# AGENTS.md - Developer & AI Assistant Guide

This document provides instructions, guidelines, and context for AI coding assistants (Gemini, Antigravity, Claude, Copilot, etc.) and human developers working on **csv-salvage**.

---

## 1. Project Mission & Architecture

- **Project:** `csv-salvage` (Fault-tolerant CSV salvage & reconstruction engine).
- **Primary Goal:** Parse and clean corrupted, malformed CSV files, rescuing data where strict parsers (Polars, DuckDB, Pandas) abort with unrecoverable `ParserError`.
- **Target Pain Points:**
  - Files generated by legacy systems with variable delimiters.
  - Unescaped newlines embedded inside unquoted or poorly quoted text cells.
  - Unbalanced or orphan quotes.
  - Inconsistent column counts (ragged rows).
  - Replacing slow, fragile Python regex cleanup scripts with high-throughput native code.
- **Core Technology (Rust):**
  - Custom finite state automaton / DFA parser (using manual state machine or `regex-automata`).
  - Schema and delimiter inference heuristics.
  - Parallel chunking and normalization using `rayon`.
  - PyO3 bindings with Maturin build backend.
- **Key Value Propositions:**
  - **"Lifesaver" Mode:** Never crashes; repairs orphan quotes or routes mathematically unrecoverable rows into a discard / quarantine stream with diagnostics.
  - **High-Throughput Parallel Processing:** Normalization and export to clean CSV files or Python dicts/tuples at native Rust speed.

## 4. Engineering Principles & Invariants

1. **Zero Panic Guarantee ("Lifesaver" Mode):**
   - The parser must **never panic** on malformed input (avoid `.unwrap()` or `.expect()` in parsing logic).
   - Use Rust's `Result<T, SalvageError>` and provide quarantine routing for unrecoverable lines.
2. **Performance & Parallelism:**
   - Prefer byte-slice streaming, zero-copy token views, and SIMD/DFA transitions.
   - Utilize `rayon` for multi-threaded chunk processing on large files.
3. **Safe PyO3 Integration:**
   - Keep the Rust core decoupled from PyO3 bindings so it can be used either as a pure Rust crate or as a Python module.
4. **CI & Workflow Invariants:**
   - `ci.yml` must stay fast (< 3 min) and run on all pushes to `main`, all PRs, and all tags.
   - `publish.yml` MUST ONLY trigger on semantic version tags (`v*`) or manual `workflow_dispatch`, and MUST wait for `ci.yml` to succeed before building or publishing.

## 5. Git Commit Conventions & Best Practices

All commits made by AI agents and contributors **MUST strictly adhere to the [Conventional Commits](https://www.conventionalcommits.org/) specification**:

```
<type>(<optional scope>): <description>

[optional body]

[optional footer(s)]
```

### Allowed Commit Types

| Type | Purpose | Example |
| :--- | :--- | :--- |
| `feat` | New feature, public API addition, or user-facing functionality | `feat(parser): add DFA state-machine quote repair` |
| `fix` | Bug fix, parser edge-case repair, or heuristic correction | `fix(tokenizer): resolve panic on unescaped trailing quote` |
| `refactor` | Code restructuring that neither fixes a bug nor adds a feature | `refactor(core): extract token buffer into reusable struct` |
| `ci` | Changes to GitHub Actions workflows, matrix builds, or release scripts | `ci(publish): gate release workflow on ci.yml completion` |
| `perf` | Code changes that specifically improve execution speed or memory usage | `perf(rayon): reduce allocator overhead during parallel chunking` |
| `test` | Adding or updating unit tests, benchmarks, or test fixtures | `test(salvage): add tests for malformed legacy CSV files` |
| `docs` | Documentation-only updates (`README`, docstrings, guide files) | `docs: explain lifesaver mode and quarantine stream in README` |
| `chore` | Maintenance tasks, dependency bumps, or tooling configuration | `chore(deps): update PyO3 to 0.29.2` |

### Rules for Agents
1. **Never use generic or lazy messages:** Commits like `"update"`, `"fix"`, `"wip"`, or `"changes"` are strictly forbidden.
2. **Use imperative mood:** Write `"add"`, `"fix"`, `"refactor"`, NOT `"added"`, `"fixed"`, or `"refactoring"`.
3. **Keep the subject line concise:** Limit to ≤ 72 characters; lowercase immediately after the colon.
4. **Scope is encouraged:** Use scopes like `(parser)`, `(ci)`, `(python)`, `(core)`, `(docs)`.
